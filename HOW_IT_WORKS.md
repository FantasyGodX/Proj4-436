# How It Works

The big picture of how GitHub, Vercel, and Supabase fit together in this project. For a line-by-line tour of the code, see [EXPLANATION.md](EXPLANATION.md).

## The big picture

```
Developer (VS Code)
   |  git push
   v
GitHub repo --(automatic webhook)--> Vercel --builds--> serverless function (the Express app)
                                                              ^   |
 Browser / REST client ---- HTTPS request ---------------------+   | supabase-js + secret key
                                                                   v
                                                          Supabase (Postgres `quests` table)
```

Three separate services, each with one job:

| Service | Job |
| --- | --- |
| **GitHub** | Stores the code and its history. It never runs anything. |
| **Vercel** | Builds and runs the code on the internet. |
| **Supabase** | Stores the data. It is a hosted Postgres database. |

## How Vercel connects to GitHub

Importing the repo into Vercel installs Vercel's GitHub app on it. GitHub then notifies Vercel on every push. Vercel clones the repo, runs `npm install`, compiles the TypeScript, and publishes the result. Pushing to `main` updates the production URL; other branches get preview URLs. Only the code flows from GitHub to Vercel. Secrets do not.

## What Vercel actually runs

Vercel does not keep a server running. It is **serverless**:

- Vercel finds `src/index.ts` because an entry file must be named `index`, `app`, or `server`.
- It sees `export default app` and turns the Express app into a function.
- When a request arrives, Vercel starts the function if needed, runs the request through the app, returns the response, and may shut the function down. The first request after idle time can be slower (a "cold start").
- Nothing can live in memory between requests, so all data is stored in Supabase.
- `if (!process.env.VERCEL) app.listen(...)`: Vercel sets the `VERCEL` variable itself. Locally it is unset, so the app listens on port 3000. On Vercel the app skips `listen`, because Vercel handles that.
- `express.static` is ignored on Vercel, and this project does not use it.

## Supabase's role

Supabase is the only place data lives. The `quests` table is real Postgres, created by running `supabase/schema.sql`. The API talks to it with `@supabase/supabase-js`, which sends requests to the project URL over HTTPS. The `Database` type in `src/types/database.types.ts` (generated by `supabase gen types`) tells TypeScript the table's columns, so a typo in a column name fails at compile time.

**Row Level Security (RLS)** is turned on for `quests` with no policies. That means public, browser-side keys cannot read or write the table at all. The **secret key** bypasses RLS, which is why the server can. The only way into the data is through this API, and the API decides what is allowed (its validation).

## Secrets and environment variables

- `SUPABASE_URL` and `SUPABASE_SERVICE_KEY` are read from `process.env`. They are never written in code.
- **Locally:** they live in `.env`, which `.gitignore` keeps out of GitHub. `tsx --env-file=.env` loads them.
- **On Vercel:** they are set once under Project Settings, Environment Variables, and injected into the function at runtime.
- Variable changes only apply to **new** deployments, so redeploy after changing them.
- If the secret key ever lands in git or is shared, rotate it in Supabase (Project Settings, API Keys) and update `.env` and Vercel.

## Life of one request

`GET https://<app>.vercel.app/quests?status=open`

1. Vercel routes the request to the function.
2. `express.json()` runs, then the logger.
3. The `/quests` router matches `GET /`. The handler validates `status=open` against the allowed values.
4. `getDb()` creates the Supabase client (the first time) from the environment variables.
5. `.from('quests').select('*').eq('status','open')` goes to Supabase, which replies with rows.
6. The handler sends `res.status(200).json(rows)`. The logger prints a line, visible in Vercel's Logs tab.
7. If anything fails along the way, the error goes to `errorHandler`, which replies with JSON.

## Local versus production

| | Local | Production |
| --- | --- | --- |
| Start | `npm run dev` (tsx, auto-reload) | Vercel builds on every push |
| Env vars | `.env` file | Vercel settings |
| Listens on | port 3000 | Vercel handles it |
| Database | the Supabase project | the same Supabase project |

Local and production share the **same database**, so a quest created locally also shows up on the live site.

## Where to look when something breaks

- **Build failed:** Vercel, Deployments, click the deployment, read the build log.
- **Runtime errors on the live site:** Vercel, the deployment, Logs tab. The `console.error` messages appear there.
- **JSON error with a message:** read it. The validation or error handler is telling you what is wrong.
- **Data looks wrong:** Supabase, Table Editor.
- **Changed an environment variable:** redeploy.

## Where each part of the grade lives

- REST design: `src/routes/quests.ts`
- Supabase integration: `src/lib/supabase.ts` and the queries in the routes
- Middleware and error handling: `src/middleware/` and `src/lib/validate.ts`
- TypeScript: `src/types/database.types.ts`
- Deployment: the live Vercel URL
- Documentation and repository: `README.md` and the commit history
